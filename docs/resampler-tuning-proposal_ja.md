# ストリーミングリサンプラーの設定改善案

初版: 2026-09-06（当初は未実装の改善案）。2026-09-07に固定モデル入力側の
Both化を採用。時間単位でFFTサイズを変更する案は未採用。

## 2026-09-07: READMEのチャンクサイズ推奨を再確認

rubato 5.0.0の同梱README、[上流READMEのUsage節](https://github.com/HEnquist/rubato/blob/master/README.md#usage)、
[Fftの仕様](https://docs.rs/rubato/latest/rubato/struct.Fft.html)と実装を確認した。
検討後、480指定の固定モデル入力側に限って`Both`を採用した。
汎用ストリーミング入力は従来どおりInput。以下の「変更前」はBoth化の直前を指す。

READMEは数百～数千フレームを一般的な目安とし、入力APIのバッファ長が固定なら
その長さ、可変なら平均に近い扱いやすい値（例: 2の累乗）から始めるとしている。
2の累乗は必須条件ではない。また`FixedSync::Both`はレート比に合う長さへ丸め、
Input／Outputモードより内部バッファ処理を減らせる、と説明されている。

本アプリのリサンプラはコールバックの直後ではなく、200 msを蓄積したワーカーから
呼ばれる。デバイスのバッファ長、モデルの200 msホップ、rubatoの呼び出し単位、
内部FFTブロック長は区別する。出力・有限RMS参照の1024指定は既に`Both`で、
READMEの有限クリップ向けの出発点にも沿っている。入力の480も一般的な目安の範囲内。

### 実際のサイズと保持時間

`resampler_chunk_probe`でrubato 5.0.0を実際に構築し、内部サイズとcutoffを取得した。
固定ホップの保持時間は本アプリの`FixedHop`で全位相周期から算出している。
200 ms入力→16 kHzの条件。以下は入力リサンプラ内の定常的な保持時間の計算値であり、
CPU処理時間やデバイス込みの実測遅延ではない。

| 入力側の指定 | 48 kHzの実FFT入力ブロック／保持時間 | 44.1 kHzの実FFT入力ブロック／保持時間 |
| --- | ---: | ---: |
| 変更前: 480、Input、分割1 | 480／5.000 ms | 882／30.000 ms |
| 512、Input、分割1 | 513／23.938 ms | 882／30.000 ms |
| 512、Input、標準の分割2 | 258／15.938 ms | 441／25.000 ms |
| 今回採用: 480をヒントにBoth、同じ窓 | 480／5.000 ms | 882／10.000 ms |

このブロック長はrubatoの`fft_size_in()`の値で、ゼロ詰めを含む実FFT変換長そのもの
ではない。512指定でもFFTブロックはレート比の整数倍へ丸められ、2の累乗にはならない。
さらに200 msホップとの位相ずれが生じるため、480を512に変えるだけでは改善しない。
標準コンストラクタへの変更も分割数・フィルタのcutoffを変えることがある。

44.1 kHzでBothが有利なのは、今の「480単位でrubatoへ渡す」「内部では882単位で処理」
という二段の待ちを、882単位に揃えられるため。200 msの8820サンプルがちょうど10ブロック
になり、FFTとフィルタを変更せずに余分な保持を減らせる。32／48／96 kHz入力では同じ
Both候補の保持時間は現在と同じ（それぞれ17.5／5／2.5 ms）。

同じFFT・窓を使うBoth候補は、32／44.1／48／96 kHzで1秒間の230 Hz＋6700 Hzの
合成波形と先頭・末尾のインパルスを変換し、フィルタ遅延を補正した全16000出力サンプルが
現行Inputモードと完全一致した。これはrubato単体の有限波形検証であり、共有パイプラインや
全ホップ条件、SOLAの選択、デバイス経路の遅延改善を検証した結果ではない。

### 判断

- 480→512の一律変更、および200 ms全体を分割1でFFTへ渡す変更は採用しない。
  後者はこのレート群ではフィルタ遅延だけで100 msになり、フィルタ特性も変わる。
- 採用対象は、固定入力ホップ専用の経路で変更前と同じFFT・窓を使う`Both`。
  特に44.1 kHz入力に利点が見込め、48 kHz入力には今回の保持時間上の改善はない。
- 汎用`StreamingResampleMono`の既定値をまとめて変えない。ノイズ除去やパススルーも
  利用するため、それぞれの保持量・リセット・末尾処理まで影響を確認する必要がある。
- 全ホップの波形一致・FIFO上限・先頭末尾・状態リセットと共有パイプラインの回帰で
  検証する。実機での定常時入出力測定は未実施。実装後の検証結果は
  [latency_ja.md](latency_ja.md)に記録する。

## 現状と目的

`crates/vc-core/src/dsp.rs` の `StreamingResampleMono` は、入力レートに
関係なく480サンプルを要求し、FFT分割数1、窓関数 `BlackmanHarris2` を使う。
480サンプルは48kHzでは10msだが、16kHzでは30msになる。
入力レートに応じた時間単位の設定にして、特に16kHzから戻す経路の待ち時間を
減らせるか検討する。

rubato 3 → 5 の移行では旧設定を明示的に維持した。移行時の同一環境での
比較では、6種類のレート組み合わせ × 5種類の入力長 × 一括処理・3種類の
ストリーミング入力分割（計120条件）で、波形と出力長がビット単位で一致した。
この結果はライブラリ移行の確認であり、本改善案の音質・遅延を保証するものではない。

## 第一候補

- ストリーミングの要求チャンク長を「入力側の約10ms」にする。
  サンプル数への丸め方は実装時に明示する。
- FFT分割数1、`BlackmanHarris2` は維持し、変更する要素を絞る。
- 低遅延の比較候補として約5msも測定する。初めから既定値にはしない。
- `resample_mono` の一括処理は1024サンプル、`FixedSync::Both` のままにする。
  この関数はWAV専用ではなく、RVCの音量参照や接合処理にも使われる。

## 遅延の理論値

rubato 5.0.0 のFFTサイズ計算と `output_delay()` に基づく。
アプリ全体の実測遅延ではない。現在の入力チャンク時間は要求値であり、
内部FFTブロックの時間とは異なる場合がある。

| 変換 | 現在の入力チャンク時間 | 現在のフィルター遅延 | 約10ms指定時のフィルター遅延 |
|---|---:|---:|---:|
| 48k → 16k | 10ms | 5ms | 5ms |
| 16k → 48k | 30ms | 15ms | 5ms |
| 44.1k → 16k | 約10.9ms | 10ms | 5ms |
| 48k → 44.1k | 10ms | 5ms | 5ms |

`FixedSync::Input` の内部FFT入力サイズは、入力レートと出力レートの最大公約数を
`g` とすると、`ceil((chunk_size / sub_chunks) / (input_rate / g)) * (input_rate / g)`
で決まる（整数除算と最小値の扱いは上流実装を参照）。
出力遅延は `fft_size_out / 2` サンプル。
44.1k ↔ 16kのような組み合わせには最小FFTサイズがあり、要求チャンクを
半分にしてもフィルター遅延が減るとは限らない。

先頭の遅延サンプルを捨てても、必要な入力が揃うまでの待ち時間はなくならない。
フィルター遅延の差を、そのままアプリの往復遅延の改善量として扱わないこと。

## 新しい標準コンストラクターとの関係

rubato 5.0.0 の `Fft::new` は分割数を `max(chunk_size / 256, 1)` とする。
現在の480サンプルでは自動設定も1になり、窓関数も同じなので、
単に `new_custom` を `new` に戻してもストリーミング設定は変わらない。
また `FixedSync::Both` のFFTサイズ決定には分割数を使わない。
明示設定を続ける目的は、将来のデフォルト変更に動作を左右されないようにすること。

## 検証と採用判断

1. 旧設定・約10ms・約5msを、同じ入力とモデルで比較する。
2. 16k・44.1k・48k間の変換、短い入力、不規則な入力チャンクを含め、
   出力長、初回出力までの入力量、連続性、先頭の遅延補正、最終尾を確認する。
3. インパルス・周波数スイープ・高域信号で周波数応答と折り返し成分を確認する。
   小さいFFTでは高域の減衰特性も変わり得るため、歯擦音、高めの声、
   ノイズ除去後の実音声も試聴する。
4. 処理時間の平均と上位パーセンタイル、CPU負荷、バッファ不足、実際の
   入出力遅延を測る。処理回数が増えるので、小さいチャンクが常に高速とは限らない。
5. ノイズ除去の往復経路では初期充填量、遅延報告、停止時の排出・トリムを
   一緒に確認する。音質と出力整合性を保ち、実測上の利点がある場合に採用する。

## 関連箇所・変更時の制約

- `crates/vc-core/src/dsp.rs`: リサンプル設定、入力蓄積、先頭の遅延補正。
- `crates/vc-core/src/denoise/adapter.rs`: ノイズ除去モデルへの往復変換、初期充填と遅延。
- `crates/vc-core/src/model_rvc/stream.rs`: 16kHz入力への変換と音量参照。
- `crates/vc-core/src/sola.rs`: 接合処理に関係する一括リサンプル。
- `crates/vc-app/src/realtime.rs`: パススルーのデバイスレート変換。
- [アーキテクチャ](architecture.md): 共通パイプラインの所有境界。

変更は共通DSP層で行い、フロントエンド別の変換経路を追加しない。
音声コールバックに推論・リサンプル処理・割り当て・ロック・ログ出力を移さない。
定数変更時は入力バッファの整理閾値や各利用側の初期充填との関係も確認する。
