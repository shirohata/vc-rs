# 固定ホップの遅延削減と検証

対象はTensorRT、チャンク200 ms、追加コンテキスト1000 ms。モデル、FFTサイズ、
フィルタ、SOLA 85 ms／探索12 ms／末尾破棄10 msを維持して、固定ホップに対して
過剰だったリサンプラの初期FIFOを縮める。README再検討後、固定モデル入力側では
480指定のまま`FixedSync::Both`を使用し、FFTの自然なブロック単位へ揃えた。

改善対象は起動して安定した後の、音声入力から対応する変換音の出力までの時間。
起動時に最初の音が出るまでの時間の短縮は、達成条件に含めない。発話中と長い
無音からの復帰を評価し、起動時の無音や宣言遅延だけを改善指標にしない。

実装・自動検証は完了。下記の実測ではデバイス経路の遅延改善と「欠落なし」は
確認できていないため、計算上の削減だけで受け入れ条件を達成したとは扱わない。

48 kHz入力から16 kHzへの変換では、初期FIFOが400サンプル（25 ms）から
80サンプル（5 ms）になる。これはコンテンツ保持時間の20 ms削減であり、
マイクからスピーカーまでの実測値ではない。44.1 kHzではホップ周期に依存する。
計算の根拠と状態の所有境界は [architecture.md](architecture.md) を参照。

25→5 msは処理周期の変更ではない。モデルへの投入は200 msのまま、48 kHz入力の
FFT処理単位も480サンプル（10 ms）のまま。変更したのは16 kHz出力FIFOの先頭に
実際に置く無音サンプル数（400→80）である。最初の200 ms入力からモデルへ渡す
200 msは、従来が「無音25 ms＋元音声175 ms」、変更後が「無音5 ms＋元音声195 ms」。
従来は既に生成できた音声20 msがFIFOに残り、その持ち越しが後続チャンクでも続く。
同じ200 msホップで、インパルス、10秒間の無音、再度のインパルスを処理する回帰
テストでは、無音後にも入力の100 ms位置のインパルスが各出力の125 ms→105 msへ
移り、全波形が20 msの平行移動だけで一致することを確認した。
200 ms分の入力を待つ時間や処理完了時刻そのものを20 ms早める変更ではない。

### 追加変更: 固定モデル入力側のBoth化

480の指定値、分割数1、`BlackmanHarris2`を維持し、固定ホップを検証した
`FixedInputResampler`だけが`Both`を選ぶ。汎用`StreamingResampleMono::new`はInputの
まま。デノイザ／パススルーのバッファ契約は変更しない。

200 msホップの44.1→16 kHzは、実FFT入力882サンプルに対して480ずつ渡す余分な
待ちがなくなり、入力側の宣言保持時間は30→10 msになる。48 kHzは5 msのまま。
ノイズ除去なし・48 kHzモデル／出力・SOLA 85／12／10 msなら、44.1 kHz入力時の
合計宣言コンテンツ遅延は137→117 ms。実機の入出力遅延の短縮を示す値ではない。

旧Inputモードとの波形比較では、入力16／32／44.1／48／96 kHz、
20／30／100／200／600 msについて双方の全位相周期を通し、遅延補正後の波形が
完全一致することを確認した。入力の実FFTサイズ、cutoff、フィルタ遅延も同一。
44.1 kHzのモデル入力・F0・生成器の時間軸は、旧汎用リサンプラで事前生成した
独立した参照波形と比較する。再初期化、先頭／末尾、WAV／遅延合成は既存の共有
パイプラインの回帰テストを使用する。

Both化後はTensorRT構成のワークスペーステスト324件、全ターゲットのClippy、
GUI／CLIのリリースビルドが成功した。入力リサンプラのCPUベンチは、直前のInput版と
Both版を順番を入れ替えて各4回測定した（200チャンクのウォームアップ、
200サンプル×20回、各実行の中央値をさらに中央値で集計）。両方ともバックエンド
機能なしのreleaseビルドで、ウォームアップ後のヒープ確保は全条件0回。

| 入力→16 kHz、200 ms | Input版（µs） | Both版（µs） |
| --- | ---: | ---: |
| 16 kHz | 0.305 | 0.310 |
| 32 kHz | 19.855 | 19.910 |
| 44.1 kHz | 35.770 | 34.935 |
| 48 kHz | 26.805 | 26.820 |
| 96 kHz | 47.285 | 46.705 |

最大の中央値増加は0.055 µs（0.000055 ms）で、この比較にミリ秒単位のCPU回帰はない。
この保持時間とCPU処理時間の結果を、実機の入出力遅延の改善量として加算しない。

追加の各2回の比較では、44.1 kHzの中央値がInput 36.595 µs、Both 40.035 µsとなったが、
Bothの2回自体が35.31／44.76 µsとばらついた。この少数回の差をそのまま回帰量としない。
そこで同じ保存済みInput版／現在のBoth版のreleaseベンチを、論理CPU 4に固定して
30組再測定した。Input→Both／Both→Inputを各15組とし、実行順を固定seedで混ぜた。
各プロセスで200チャンクをウォームアップ後、200サンプル×20回を測る。
全体の事前ウォームアップも両版1実行ずつ行い、集計からあらかじめ除いた。
このCPU指定は計測プロセスだけに適用し、製品の設定は変更していない。

| 入力→16 kHz、200 ms | Input中央値（µs） | Both中央値（µs） | 組ごとの差の中央値（µs） | Bothが遅かった組 |
| --- | ---: | ---: | ---: | ---: |
| 16 kHz | 0.3097 | 3.1140 | +2.80185 | 30 / 30 |
| 32 kHz | 19.945 | 20.125 | +0.210 | 28 / 30 |
| 44.1 kHz | 36.200 | 35.305 | −0.925 | 0 / 30 |
| 48 kHz | 26.850 | 27.095 | +0.265 | 26 / 30 |
| 96 kHz | 47.025 | 47.620 | +0.550 | 28 / 30 |

中央値同士の差と、各組の差を集計した中央値は一致するとは限らない。
組単位の差を10,000回bootstrapした95%区間は、32／48／96 kHzでそれぞれ
[+0.165, +0.220]／[+0.210, +0.295]／[+0.450, +0.620] µsだった。
この測定条件内で繰り返す小さな差は残るため、「すべて誤差」「CPU回帰が完全にゼロ」
とは結論しない。48 kHzの+0.265 µsは+0.000265 msで、200 msチャンクの約0.00013%。
以前の44.1 kHzの+3.44 µsという悪化は再現せず、今回は全30組で高速だった。

16 kHzは両版ともFFTを使わないコピー経路である。それでもCPU固定時だけ大きな差が
出たため、CPU固定なし／論理CPU 4／論理CPU 6で追加3組ずつ確認した。固定なしでは
Input 0.305〜0.355 µs、Both 0.270〜0.380 µsとなり、約+2.8 µsの差は消えた。
CPU 4／6固定では約+2.8 µsが再現した。これは測定条件に依存する差として残し、
BothのFFT処理が原因とは扱わない。別実行ファイル間の比較なのでコード配置などの
影響も分離しておらず、bootstrap区間は同じ条件内の再現性だけを表す。
今回の全入力条件でもウォームアップ後のヒープ確保は0回。生ログと組単位の結果は
ローカルの`tmp/latency-check/paired-cpu-summary.json`、CPU指定の追加確認は
`tmp/latency-check/affinity-sanity.json`に保存した。音声I/OとTensorRTは今回測っていない。

以下の2026-09-07のワーカー／デバイス／CPU測定は、特記しない限りBoth化より前の
記録である。Both化した実機の連続運転・聴感・入出力遅延は再測定していない。

## 無音時の出力キュー抑制との関係

CLI／GUIのワーカーは、出力が無音判定され、追加前の出力リングの残量が1チャンク
（200 ms）を超えると、新しく生成した無音チャンクの追加を見送る。既にキューに
あるサンプルを直接削除する処理ではなく、再生によって余分な滞留を減らす。
残量が1チャンク以下なら追加するため、追加直後は最大2チャンクになり得る。
この判断は変換後に行い、入力リサンプラやモデル、平滑化の状態はリセットしない。
したがって出力キューの滞留解消と、内部リサンプラの保持時間は別々に評価する。

無音チャンクの意図的な追加見送りは、リング容量不足を数える既存の
`output_dropped_samples`には加算されない。この値が0でも、無音の追加見送りが
なかったとは判断できない。現在の約1秒間隔のキュー残量・欠落カウンタだけでは、
個々の発話の遅延を入力待ち・処理・出力待ちに確実に分解できない。内部FIFOの
回帰テストが成功しても、定常状態のデバイス経路で同量短縮することの証明にはならない。

## 自動検証

- 入力16／32／44.1／48／96 kHz、モデル32／40／48 kHz、出力44.1／48 kHz、
  ホップ20／30／100／200／600 msについて全位相周期を検証。
- 生の連続FFT出力との波形一致、最小FIFO量、固定出力長、FIFO容量、先頭・末尾、
  無効ホップの拒否、リセット後の再現性を検証。
- RMS参照用の独立ウィンドウは、FFTと作業領域だけを再利用する。信号履歴は
  毎回リセットする。波形誤差1e-6以下と、ウォームアップ後のヒープ確保0回を検証。
- 既存の有限WAV変換、SOLA／PSOLA、遅延合成・丸めの回帰テストも実行する。


## ワーカー測定の再現

`vc-app`の`latency_probe`は実際の共有`RvcPipeline`と`ChunkConverter`を使い、
音声を200 ms間隔で投入する。デバイス、コールバック、キューは含まない。
20チャンクのウォームアップ後、全チャンクの推論時間・処理全体時間・投入時刻の
遅れ・期限超過をメモリに記録し、終了後にCSVを出力する。ロードとエンジンビルドは
測定外。同じWAVを繰り返すため、ループ境界は聴感評価には使わない。

```powershell
. ./scripts/activate.ps1
cargo build --release --manifest-path tools/tensorrt_builder/Cargo.toml
$env:VC_RS_TENSORRT_BUILDER_HELPER = (Resolve-Path tools/tensorrt_builder/target/release/vc-tensorrt-builder.exe).Path
cargo build --release -p vc-app --example latency_probe --no-default-features --features tensorrt,rnnoise,gtcrn
# 各パスは使用者が指定する。設定はソース先頭の説明を参照。
./target/release/examples/latency_probe.exe MODEL.onnx EMBEDDER.onnx F0.onnx INPUT.wav REPORT.csv 600 tensorrt
```

比較時には同じモデル・音声・バックエンド・キャッシュ・電力設定を使用し、
両方の測定を同時に動かさない。GUI／CLIの`Processing (total)`は平滑化と出力側
リサンプリングを含む。`Content delay (nominal)`はデバイス、キュー、入力チャンク
蓄積、処理時間を含まず、未初期化・パススルーでは不明として扱う。

## デバイスを含む測定

仮想ケーブルへ既知の音声を再生し、ケーブルのCapture側を変換入力にする。
変換音は別のRender先へ送り、入力Captureと出力RenderのWASAPIループバックを
共通QPC時刻で記録する。同じケーブルを変換入力と変換出力の両方には使わない。
これはWindows音声経路を含む測定であり、マイク・DAC・スピーカーの物理遅延は含まない。

声質とピッチが変化するため、入出力のサンプル一致から遅延を求めない。無音で
区切った同じ発話を反復し、振幅包絡の対応と発話開始位置を確認する。起動直後と
停止処理は定常状態の欠落カウンタから分ける。収録側の不連続・時刻エラーも
併記し、推論時間や宣言遅延の減少だけを実測の改善と扱わない。

### TensorRTを使わない変更箇所のCPU比較

受け入れ判断について、使用者からTensorRT推論時間の変動はいったん除外し、
それ以外の処理の回帰を確認する方針が示された。このため200 ms固定ホップの
`fixed_resample`ベンチと、同じ模擬モデル出力を使う
`pipeline::model_free_pipeline_bench::fixed_200ms_conversion`を追加した。
前者は実際の非公開DSPモジュールを直接コンパイルし、後者は共有`ChunkConverter`
を呼ぶ。ベンチ用にリサンプラの公開APIを広げたり、処理を複製したりしない。

比較元`2cd09be`には同じベンチを載せ、旧APIに合わせてコンストラクタの引数だけ
調整した。CPU本体の実装は旧版のまま。両方とも同一Cargo.lock・バックエンド機能なしの
releaseビルドを使い、各ケースで200チャンクをウォームアップしてから
200サンプル×20回を測定。順番を前→後→後→前→後→前→前→後とし、各4回の
中央値をさらに中央値で集計した。コンパイルと測定を同時実行しなかった。

| 32 kHz | 23.840 | 23.425 |
| 44.1 kHz | 43.430 | 44.520 |

| 96 kHz | 58.040 | 59.090 |

全17ケース、全8実行でウォームアップ後のヒープ確保は0回。入出力リサンプラの
中央値の最大増加は1.760 µs、出力処理全体では5.750 µsだった。微小な増加はあり、
「CPU処理は全く遅くなっていない」とは扱わないが、この比較でミリ秒単位の回帰は
見つからなかった。出力処理全体は出力リサンプラを含むため、両者を加算しない。

この比較は変更したCPUの主要部分と出力処理の境界を調べるもので、実モデルの
前後処理全体からTensorRT呼び出し時間を厳密に差し引いた計測ではない。
デバイス・ワーカーの待ち時間も含まない。既存の`inference_time`にはRVCの前後処理も
含まれるため、以前の約8 msの増加をTensorRT単体の変動と確定する根拠にはしない。

### CABLE経由の連続測定

同じ音声をCABLE Inputへ再生し、44.1 kHzのCABLE Outputを変換入力、48 kHzの
別のヘッドセットRenderを変換出力に使用した。双方のCapture／Renderループバックを
ネイティブレートで録音し、各パケットのQPC時刻から共通1 msグリッドの振幅包絡を
復元した。2秒の無音を挟んだ同じ母音音声を各10分再生し、起動・末尾付近を除いた
143発話の包絡相関から100～800 msの範囲で遅延を推定した。

| 項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| この経路の宣言コンテンツ遅延 | 147.875 ms | 137.000 ms |
| 包絡から推定した遅延p50 | 470 ms | 576 ms |
| 包絡から推定した遅延p95 | 591 ms | 585.9 ms |

キューとカウンタは既存の約1秒間隔のCLIスナップショットから集計し、最初と最後の

アンダーランは悪化した。この結果から実測遅延の改善・安定性の維持を認定しない。

### 有限WAVと音質の比較

無音からの復帰、母音、子音を含む同じ22.91秒の音声を48 kHzで変換した。
両方とも1,099,680サンプル、クリッピング0、最後の200 msのRMSは0だった。
10 ms窓の音量包絡相関は0.9892。振幅のある77境界（前後いずれかのRMSが0.001以上）で、
境界の隣接サンプル差の最大は0.01545→0.02195、局所的な通常の差に対する比率の
p95は2.866→3.091だった。境界の位置は各バージョンの遅延補正に従う。

リサンプラ単体の波形一致とは別に、入力の保持時間変更でモデル窓とSOLAの選択は
変わるため、変換済みWAV全体のサンプル一致を期待しない。これらの客観指標だけで
クリックや音質劣化がないとは断定できない。比較WAVについて使用者から
「劣化は聞き取れない」と確認を得た。これはこの22.91秒の聴感比較の結果であり、
連続音声経路で発生したアンダーランとは別に記録する。
