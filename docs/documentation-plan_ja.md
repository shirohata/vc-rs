# 特長の整理とドキュメント改善計画

2026-09-14。現行チェックアウトの実装・説明を基にした計画。
README改稿とバックエンドガイドの初稿は作成済み。新たな性能測定は未実施。
リリース向けの文章に反映する際は、配布タグにも各機能が含まれることを確認する。

## 訴求の軸

第一の軸は **ネイティブTensorRTによるNVIDIA GPU向け推論と、GUI・VST3での利用**。
**GPUに合わせたバックエンド選択**を主役に含め、MIGraphX・OpenVINOはWindows ML経由の
実験的対応として紹介する。続けて **Python環境不要の導入、既存RVCモデルの利用** を伝える。
Rustや内部設計は、利用者のメリットを説明した後に根拠として置く。

冒頭コピー案:

> NVIDIA GPUのためのネイティブTensorRT対応RVCボイスチェンジャー。
> 単体アプリでも、DAWのVST3プラグインとしても使えます。
> Python環境の準備は不要。Windows ML版ではDirectML経由でNVIDIA以外のGPUも利用できます。

これは方向性を示す案であり、他製品に対する速度の優位を主張するものではない。

| 優先度 | アピールポイント | 利用者への価値・掲載案 | 根拠と条件 |
| --- | --- | --- | --- |
| 主役 | ネイティブTensorRT | NVIDIA GPU向けに最適化した推論経路を選べる | [native_tensorrt.rs](../crates/vc-core/src/model_rvc/native_tensorrt.rs)。ContentVec・RMVPE・RVCの3段に対応。固定shapeとエンジンキャッシュを活用。初回構築・設定変更時の待ち時間も併記する |
| 主役 | VST3として使える | DAW内で音声変換し、ピッチ等を自動化、設定をプロジェクトに保存できる | [VST3 README](../crates/vc-vst3/README.md)。Windows ML/TensorRTの配布形態。遅延報告はモニター遅延を消す機能ではない |
| 主役 | Python / PyTorch環境不要 | ビルド済みアプリから始められ、Pythonの依存関係管理が不要 | [README](../README.ja.md)、[変換器](../crates/vc-convert/src/lib.rs)。GPUランタイム・モデルの準備は別途必要 |
| 補強 | アプリ内PTH→ONNX変換と補助モデル取得 | 既存の声モデルを持っている人が導入しやすい | [README](../README.ja.md)、[オンボーディング](onboarding.md)。PTH変換はRVC v2/F0モデルに限定。全PTH対応とは書かない |
| 補強 | Windows ML / DirectML | NVIDIA以外のGPUでも試せる選択肢 | [README](../README.ja.md)。全GPUでの性能保証や、全EP・NPUの実機検証済みという意味にはしない |
| 補強 | 音声処理と推論を分離 | 推論待ちで音声コールバックを止めない設計 | [設計](architecture.md)。過負荷時の音切れ防止を保証する表現にはしない |
| 応用 | CLIと共有変換パイプライン | WAV変換・スクリプト化・条件を揃えた検証ができる | [CLI](cli_ja.md)、[設計](architecture.md)。WAVの開始・末尾処理や実時間I/Oには差があるため、出力の完全一致を保証しない |

ノイズ除去、モデル情報表示、ライブ調整などは使い勝手の補強として利用ガイドに置く。
README冒頭の特長は4〜5項目に絞り、すべての機能を同じ重さで並べない。

## 現READMEで見直す表現

| 現状 | 改善方針 |
| --- | --- |
| 最初の特長が「ネイティブRust実装」 | TensorRTと具体的な利用場面を先にし、実装言語は根拠に回す |
| TensorRTが「幅広いGPU対応と最速モード」の一部 | 独立した特長に昇格。「NVIDIA GPU向けネイティブTensorRT対応」と具体化する |
| 「最速」「処理時間の最悪値が安定」 | 比較対象や測定がない断定を外す。Rust採用だけから最悪時間の安定を導かない |
| 「同じRVCモデルなら他ツールと音質は本質的に同等」 | 音質はモデルに加え、F0、前後処理、チャンク、エクスポート等にも依存すると整理する。優位・同等の断定は試聴比較後に行う |
| 「配布も軽量」「数MB」 | アプリZIP、外部ランタイム、補助モデル、構築後キャッシュを区別。配布物の最新サイズを確認し、TensorRT版まで軽いという印象を避ける |
| PTH変換・補助モデル取得が手順内に埋もれている | 「既存モデルから始めやすい」と特長で短く紹介し、対応範囲を隣に置く |
| 「WAVで決定論的に検証」 | 固定入力・設定等で比較検証しやすいと説明。全バックエンドのビット一致は主張しない |

## 競合比較の扱い

「ほかにはない」「唯一」は現時点では採用しない。
[rvc-playerの公式README](https://github.com/theArcsin/rvc-player)にも
ONNX RuntimeのTensorRT execution provider用ランタイムへの言及がある
（2026-09-14確認）。これは対応実態や速度の検証ではないが、TensorRTという名称だけで
独占的な機能と断定する根拠が足りないことを示す。

必要になった場合は、まず [VCClient](https://github.com/w-okada/voice-changer) 等の
具体的な比較対象・バージョンを選び、公式ドキュメントと実装を調べる。
比較軸は「ネイティブTensorRTかORT EPか」「3段推論の対象範囲」
「配布済みか」「GUI/VST3の対応」「導入手順」「実測性能」とする。
未記載を非対応と扱わず、未確認と記す。現段階で網羅的な競合比較表は作らない。

## 実施順序と成果物

### P0: READMEの入口を改善する

- [ ] [日本語README](../README.ja.md)と[英語README](../README.md)を同じ構成で改稿する。
- [ ] 冒頭を「何ができる → TensorRTを含む特長 → GUI/DAWの利用例 → ダウンロード」の順にする。
- [ ] 上記の根拠不足の断定を修正し、モデル形式・OS・初回構築の条件を選択箇所に残す。
- [ ] パッケージ選択を「単体/DAW」と「Windows ML/TensorRT」の2軸で説明する。
- [ ] 現行配布タグ・ZIPサイズ・依存ランタイムを[配布手順](distribution.md)に沿って確認する。

完了条件: 冒頭だけで「何が特徴か、自分の用途で使えるか、何をダウンロードするか」が分かり、
日英で対応範囲・制約・性能表現が一致する。

### P1: TensorRTの利用案内とDAWの使い方を整える

- [ ] 利用者向け `docs/tensorrt_ja.md` / `docs/tensorrt.md` を作る。
  対象環境、3段推論、初回構築と再利用、再構築される条件、容量、設定の決め方、トラブル対処を扱う。
- [ ] ネイティブTensorRT配布版とWindows MLのTensorRT-RTX EPを区別して説明する。
- [ ] [性能調査](tensorrt_performance_ja.md)は技術資料として残し、新ガイドから参照する。
- [ ] [VST3 README](../crates/vc-vst3/README.md)の先頭に導入・モデル設定・オートメーション・
  保存/復元の利用例を置き、内部設計を後ろへ移す。遅延補償の意味も説明する。
- [ ] 初回セットアップとDAW内利用の画面例を用意する。公開画像に個人パスや未許諾モデル情報を含めない。

完了条件: READMEから用途別の操作手順に到達でき、TensorRT初回準備を経て使い始める流れが追える。

### P2: 性能を測り、訴求を数字で補強する

- [ ] 同じPC・モデル・音声・チャンク・追加文脈・音質設定で、まずvc-rs内のTensorRTとWindows MLを比較する。
- [ ] CPU/GPU、ドライバ、SDK/EP、アプリcommit、モデル識別情報、設定、ウォームアップ、測定時間を記録する。
- [ ] 推論単体、DSP込みワーカー処理、デバイス入出力遅延を別々に測る。
  定常処理のp50/p95/p99、測定中の最大値、音切れカウンタ、GPUメモリ、初回構築・キャッシュ利用時の起動時間を記載する。
- [ ] 会話・持続母音・歌唱・無音からの復帰で試聴し、小チャンク設定の音質も確認する。
- [ ] 再現手順と条件付きの結果を公開し、その結果で言える範囲をREADMEに短く掲載する。

既存の性能調査はRTX 3060 Ti、TensorRT 11.0.0.114 / CUDA 13.2での
`trtexec`測定。現在の開発SDKやアプリ全体の測定として使わない。
3段それぞれのp95の和は、パイプライン全体の実測p95ではない。
13.91 msを「ボイチェンの遅延14 ms」と宣伝しない。
[遅延検証メモ](latency_ja.md)でも実機確認が未完了の項目があり、設計値と実測値を分ける。

完了条件: 速度・遅延・安定性の数字から測定条件と再現手順に辿れ、音質上のトレードオフも判断できる。
P0/P1は測定完了を待たず、機能上の事実だけで進められる。
